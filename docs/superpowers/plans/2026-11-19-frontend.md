# Frontend de Lifex: plan de implementación

> **Para quien ejecute:** usar superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans para llevar este plan tarea por tarea. Los pasos usan casillas `- [ ]`.

**Meta:** construir el frontend real de Lifex: la web pública idéntica al prototipo `FRONTEND-WEB/web` conectada a la API, y el panel admin con shadcn.

**Arquitectura:** una sola app Vite + React + TypeScript en `frontend/`. La web pública copia el marcado y `lifex.css` del prototipo sin tocarlos; el admin (Tailwind + shadcn) es un trozo cargado aparte al que se entra con navegación completa. El servidor es la fuente de verdad (TanStack Query); el estado del asistente de compra vive en Zustand; los asientos se actualizan por WebSocket.

**Stack:** Vite, React 19, TypeScript, react-router, TanStack Query, TanStack Table, Zustand, Zod (`@lifex/shared`), Vitest + Testing Library, Tailwind v4 + shadcn (solo admin).

**Diseño:** `docs/superpowers/specs/2026-11-19-frontend-design.md` (se lee junto a este plan).

> **Actualización de estructura (2026-11-19).** El frontend quedó como **dos proyectos Vite separados** dentro de
> `frontend/`: `web/` (web pública, URL `/`), `dashboard/` (login + panel, URL `/dashboard`) y `public/` (activos
> compartidos). Donde este documento dice "rutas `/admin`" o "`app/admin`", léase `/dashboard` y el proyecto
> `frontend/dashboard`: el login es `/dashboard/login` y el panel `/dashboard`. Se despliegan juntos con
> `npm run build` y `npm start` en `frontend/` (ver README).

## Restricciones globales

- La web pública **no cambia de diseño**: mismo CSS (`lifex.css`), fuentes Jost y Hanken Grotesk, textos del diccionario es/en, iconos SVG propios. Sin Tailwind ni shadcn en ella.
- Rutas públicas en inglés: `/`, `/results`, `/fares`, `/summary`, `/passengers`, `/customize`, `/seats`, `/payment`, `/confirmation`, `/credits`. Admin: `/admin/login`, `/admin`.
- El botón "Iniciar sesión / Log in" del encabezado va a `/admin/login`. Todo salto público↔admin usa `<a href>` (carga completa), nunca el router.
- Español muestra COP, inglés USD. COP = USD × `iataTrm`. Idioma guardado en `localStorage` clave `lx-lang`.
- Los datos de la API se validan con los esquemas de `@lifex/shared` (alias `@lifex/shared` → `../shared/src/index.ts`).
- Cabecera `Idempotency-Key` (`IDEMPOTENCY_KEY_HEADER`) en el pago; WS en `WS_PATH`; `/auth/refresh` y `/auth/logout` llevan la cabecera `x-csrf-protection` y `credentials: "include"`.
- Login del admin: el paso 1 solo valida el formato del correo (no consulta si existe).
- Logo de correos: `lifex-concept2-vertical-slogan-color-1200w.png`, `width=200`, cabecera de plantilla blanca.
- Sidebar admin: logo horizontal abierto; solo icono colapsado o en móvil. El login usa el logo horizontal.
- `npm run verify` del backend debe seguir en verde en cada tarea de backend.
- El proyecto puede no ser un repositorio git: donde diga "checkpoint", si `git rev-parse` funciona haz commit; si no, deja el comando de verificación en verde.

## Foco de revisión

Casos que el diseño implica y que ninguna tarea probaría por sí sola; cada uno tiene su prueba en la tarea indicada.

1. Entrar directo a `/payment`, `/seats` o `/confirmation` sin reserva ni token: debe redirigir a `/` o al paso válido, nunca romper (Tarea 8).
2. Caduca el bloqueo del asiento (o la reserva) mientras el usuario está en `/payment`: mensaje claro y vuelta a `/seats` (Tarea 11).
3. Doble clic en "Pagar" o reintento tras timeout: se reutiliza la misma `Idempotency-Key`, no se crea un segundo pago (Tarea 11).
4. WebSocket caído en medio de la elección de asiento: reconexión, snapshot por REST y asiento ocupado visible; un hueco de `version` fuerza refetch (Tarea 6).
5. Cambiar el idioma a mitad del flujo: precios y fechas se recalculan sin perder los datos ya escritos (Tareas 4 y 8).
6. Vuelo agotado (`soldOut`) o cancelado en resultados: se muestra marcado y no se puede elegir (Tarea 8).
7. API caída o 429: pantalla de aviso con los estilos existentes y opción de reintentar (Tarea 5).
